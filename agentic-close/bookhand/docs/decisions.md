# Decision log

Bookhand was built autonomously from a single brief, with no opportunity to ask questions. Every judgment
call is recorded here with the alternatives considered, so a reviewer can disagree with a specific decision
rather than reverse-engineer it. Newest decisions are at the bottom of each section.

## Product and scope

| # | Decision | Why | Alternatives considered |
|---|---|---|---|
| P1 | Name the product **Bookhand** ("a hand on the books"), with an original mark (ledger lines and a check) and a forest-green/amber palette. | Original identity; nothing borrowed from Ramp or any other company. | Generic names ("CloseAI"), which collide with real products. |
| P2 | The demo company is **Brambleway Software (fictional)**: a US parent (USD) and a UK subsidiary (GBP), twelve closed months (Sep 2025 to Aug 2026) and an open September 2026 with planted issues. All emails and domains use the reserved `.example` TLD; the ontology IRI is `https://bookhand.example/...`. | Multi-entity and multi-currency make intercompany, FX and consolidation real. `.example` cannot collide with a real organization. | Single-entity seed (too easy); a real company's numbers (not allowed). |
| P3 | The scenario's business date is **Fri Oct 2, 2026 (WD2)** and every screen speaks in workdays (WD1 to WD5). | A close is run against a calendar; WD2 means some work is done and most is ahead, which demonstrates "what's next". | Real "today" (would make the seeded close permanently late). |
| P4 | Planted issues: a missing recurring bill (Nimbus), a received-not-invoiced PO (Fieldnote $24,000), a late invoice (Brightline $15,000), a duplicate vendor payment (Copperline $18,400), an expensed laptop that should be capitalized ($14,800), an outstanding check, a deposit in transit, an unexplained bank debit, an intercompany fee mismatch, a conference-driven flux, an unscheduled insurance prepayment, a self-approved revenue journal from the legacy ERP, and a bank memo containing a prompt injection. | Each one exercises a different skill and a different control; the integration test, the skill evals and the e2e test assert every one is found. | Random noise only (cannot prove anything). |
| P5 | "Done" = a person can open the product, sign in and close the month end to end. The demo script is the e2e test. | Mirrors the brief's definition of done. | Component demos. |

## Architecture

| # | Decision | Why | Alternatives |
|---|---|---|---|
| A1 | TypeScript end to end: domain, agent framework, API, server and React UI in one repository, one language. | One type system from database row to screen; the browser demo can run the real application. | Python backend + TS frontend (duplicated types, no in-browser demo). |
| A2 | A **persistence port** (`Db`/`Tx`) with two adapters: `SqlDb` (PostgreSQL via `pg`, or PGlite, the Postgres 17 engine compiled to WASM, for zero-setup local runs) and `MemoryDb` (a TypeScript constraint engine used by the browser demo and fast tests). | Production runs on real Postgres; `npm run up` needs no database install; the static demo needs no server. A shared conformance suite runs the same violations against every adapter. | ORM (hides the invariants we want in SQL); SQLite (different semantics from production). |
| A3 | **Invariants live in the database**: triggers enforce balanced posting, immutability of posted journals and their lines, open-period posting, reversal-only corrections, append-only tables and the audit hash chain (`db/migrations/0002_invariants.sql`). The memory adapter mirrors them. | Controls must hold even if application code has a bug or someone uses SQL directly. | Application-only validation. |
| A4 | Posting is a **state transition** (`pending_approval` to `posted`) that the database validates; entries are never inserted as posted. | One code path for every post, checked at the lowest layer. | Insert-as-posted with app checks. |
| A5 | Audit log is **hash-chained** (`sha256(prev_hash + "\n" + canonical JSON)`), append-only, serialized per tenant with an advisory lock, and verifiable from the UI and CLI. | Tamper evidence that an auditor can recompute. | Plain log table. |
| A6 | A **transport-agnostic API kernel** (auth, CSRF, rate limits, RBAC, validation, error mapping) behind a thin Node HTTP server; the browser demo calls the same kernel in-page. | Security logic exists once and is exercised by the demo, the tests and the server alike. | Express/Fastify middleware (would not run in the browser). |
| A7 | Money is integer minor units everywhere; FX via a rates table; consolidation translates per ASC 830 (closing rate for balance sheet, average for P&L, historical for equity, difference to CTA). | No float drift; standard-conformant consolidation. | Decimal libraries; ignoring translation. |
| A8 | Generated artifacts are committed and freshness-tested: the schema SQL (`0001_schema.sql`), the ERD (`docs/erd.md`), the ontology exports and the skills bundle. | Docs cannot drift from code. | Hand-maintained docs. |
| A9 | The PostgreSQL driver runs one statement at a time per transaction connection, chaining concurrent reads explicitly; COMMIT and ROLLBACK wait for anything in flight. | Use cases read in parallel (`Promise.all`) inside a transaction; node-postgres' implicit client queue is deprecated and removed in pg 9. | One connection per read (breaks transactional reads). |
| A10 | The **MCP server** is a thin stdio adapter over the HTTP API, authenticated with a personal access token, and implements the protocol directly (JSON-RPC 2.0, tools only, protocol versions 2024-11-05 to 2025-11-25) rather than through an SDK. | It cannot bypass anything: authentication, RBAC, limits, SoD, rate limits and audit all happen in the same kernel as the web app, and it works while the server holds PGlite's single connection. A dozen small messages did not justify another dependency to audit. | Opening the database from the MCP process (duplicates authorization; impossible with PGlite); the MCP SDK. |

## Ontology

| # | Decision | Why | Alternatives |
|---|---|---|---|
| O1 | A formal, versioned **close ontology** written in TypeScript (classes, relations, individuals, executable axioms, bibliography), v1.3.0, exported to Turtle and JSON-LD. Grounded in REA (McCarthy 1982), XBRL GL, the US-GAAP taxonomy, FIBO, COSO 2013 and PCAOB/ISA. | Executable and type-checked; the same objects validate entries, ground tools and explain terms in the UI. | OWL file edited in Protégé (not executable in the app); no ontology. |
| O2 | The ontology is **used**, not decorative: axioms validate every journal entry, reconciliation, flux line and schedule before posting; tool descriptions and skill inputs/outputs are typed with ontology classes; transaction coding buckets spend with ontology bucketing profiles (keywords, MCC, capitalizable); every dotted term in the UI opens its definition; the explorer browses and graphs it. | The brief requires executable validation, grounding, bucketing, hover explanations and an explorer. | |
| O3 | Every database table maps to an ontology class, and every class that names a table names a real one (unit-tested). v1.3.0 added the classes that were missing (bank account, corporate card, flux line, agent step, run budget). | Keeps the data model and the semantic layer aligned. | |

## Agent framework

| # | Decision | Why | Alternatives |
|---|---|---|---|
| F1 | A **domain-agnostic framework** (tools, proposal handlers, skill engines, pack runtime) with accounting as the first pack. The framework's own tests drive it with a tiny "notes" pack. | Reusable runtime; proves the separation. | Accounting logic inside the runtime. |
| F2 | **Skills are SKILL.md files**: YAML frontmatter is a strict typed manifest (inputs/outputs typed with ontology classes, allowlisted tools, permissions, controls, autonomy bounds, thresholds, plain-English rules, materiality basis, budgets, evals), and the Markdown is the model's instructions. Bundled into a generated module so the same skills load in Node and the browser. | Matches the Agent Skills format; reviewable as documents. | Code-only skills. |
| F3 | **Agents change nothing directly.** Tools only read; the only writes go through `propose_*` tools that create proposals, which are verified (generic checks plus the handler's ontology-based checks) and then disposed by the autonomy policy or a person. | Every change has a why, a confidence, evidence and verification. | Agents with write tools. |
| F4 | **Workpapers vs. books.** Reconciliation and flux workpapers may be refreshed directly by tools (they are working documents); anything that changes the books, a sign-off or a person's judgment goes through a proposal. | Keeps the approval queue for decisions, not bookkeeping noise. | Proposals for every workpaper refresh (floods the inbox). |
| F5 | **Autonomy L0 to L3** with a fixed disposition order: failed verification blocks; L0 suggests; L1 queues; L2/L3 auto-apply only when no risk flag is set, no `require_review` rule matches, confidence clears the floor, and the amount is under the limit (rule, threshold or trivial materiality at L2; a share of performance materiality at L3), capped by any `max_auto_amount` rule. Auto-applied items are sampled for post-hoc review (deterministically by hash). | Mirrors how controllers delegate: bounded by materiality, reviewed after the fact. | Confidence-only gating. |
| F6 | **Agents never exceed their requester**: a skill's run permission is checked at start, every tool call re-checks the tool's permission against the requester, and the orchestrator skips child skills the requester may not run (recorded in the trace). | Prevents privilege escalation through agents. | Agents as a superuser service account. |
| F7 | **Durable runs**: every tool call is journaled with an idempotency key (`sha256(run|tool|canonical input|occurrence)`); a crashed run resumes and replays journaled calls instead of repeating them; trace steps are keyed so a resumed trace has no duplicates; budgets (steps, tool calls, tokens, cost) stop runaway runs. A fault injector proves it in tests. | Recoverable, auditable, bounded. | Fire-and-forget jobs. |
| F8 | **Proposal identity**: proposals carry natural keys; a newer pending proposal supersedes the older one, applied ones are never re-proposed, and an unchanged proposal a person rejected is not proposed again. | Re-running agents is safe and idempotent. | Duplicates on every run. |
| F9 | **Prompt-injection hygiene** in depth: third-party text reaches the model only inside tool results wrapped as untrusted data; instruction-like text is detected in tool output, recorded in the trace and raised as a risk flag on any proposal that relies on it (which disables auto-apply); the model can only call allowlisted typed tools, and every proposal is verified deterministically. | Bank memos are data, never instructions (the brief). | Prompt warnings only. |
| F10 | The runtime **yields to the event loop before every tool call**. | Embedded databases resolve queries without real I/O, so a run would otherwise starve HTTP requests (server) and rendering (browser demo). Found by the e2e test. | Worker threads (heavier; PGlite is single-connection anyway). |
| F11 | **The close keeps moving by itself**: after approvals, sign-offs or flux approval, the orchestrator starts again for tasks that just became ready, on behalf of whoever started the close agents (trigger "orchestrator"), limited to skills that person may run, idempotent per set of newly ready tasks. | Orchestration across the close calendar without asking people to press "run" five times. | Manual reruns; a cron. |

## Close controls

| # | Decision | Why | Alternatives |
|---|---|---|---|
| C1 | **Flux sign-off is the Controller's approval.** The flux task cannot be signed off until every flux analysis for the close is approved; approving the analysis also signs the task off (one decision, recorded on both objects). | Otherwise a reviewer could sign off the task, and the package could go out, over variance commentary nobody approved. Found while capturing screenshots. | Two independent sign-offs (easy to do in the wrong order). |
| C2 | **The close package starts from signed-off work only** (every earlier checklist task done, not merely prepared), and a package generated over open work stays a draft: its proposal fails the BLOCKERS check, so it cannot be approved until the work is finished and the package regenerated. | A "Final" package asserts the close is complete. Other tasks may start once their inputs are prepared (F11), but the summary of the period may not. | Approving with a warning (produced a Final package that said flux was unapproved). |
| C3 | **Monetary items are denominated by what they are**: a GL cash account mapped to a bank account is denominated in the bank account's currency, so FX revaluation never remeasures a functional-currency bank account, even when foreign-currency wires were paid from it (the bank converted; the GBP account moved in GBP). | Found by the e2e test: the UK bank reconciliation could never tie because the FX agent had remeasured the GBP account. Fixed in the tool and in the seed, with an eval asserting the account is left alone. | Treating any foreign transaction currency on an account as a foreign balance. |

## Live model (Claude)

| # | Decision | Why | Alternatives |
|---|---|---|---|
| L1 | **Two engines, one contract.** Each skill has a deterministic offline engine that drives the same typed tools a live model would. With `ANTHROPIC_API_KEY` set, agentic skills run on Claude through the official `@anthropic-ai/sdk`; without it, the offline engine runs and the UI labels it "Offline agents (deterministic)". Deterministic skills (the orchestrator) never call a model. | Works with no key, reproducible tests and evals, and the live path is a drop-in. | Live-only (untestable, needs a key to demo). |
| L2 | Default model `claude-opus-5-5`; `claude-sonnet-5-5` and `claude-haiku-5-5` selectable with `BOOKHAND_LLM_MODEL`. | Current model family; Opus for judgment-heavy close work. | |
| L3 | Beta Messages API, **streamed** and collected with `finalMessage()`; `max_tokens` 32,000 (thinking counts toward it); **adaptive thinking** with summarized display (shown in the run trace); `output_config.effort: "medium"`; **server-side refusal fallback** `fallbacks: "default"` with `server-side-fallback-2026-07-01` (off for Haiku, which has none); system prompt cached with `cache_control: ephemeral`; tools sorted by name for cache stability. | Long agentic turns need streaming; Opus 5.5 always thinks and effort is the control; refusals fall back server-side. | Non-streaming (request limits); manual thinking budgets (rejected by current models). |
| L4 | The conversation history is **append-only**: assistant turns (thinking blocks included) go back exactly as received; a tool call cut off by `max_tokens` is answered with an error `tool_result` rather than editing the turn; `pause_turn` continues; `refusal` fails the run with a clear message. | Current models bind thinking blocks to the exact prior conversation; editing history would invalidate them. | Stripping truncated blocks (edits history). |
| L5 | The live path is unit-tested with **recorded SSE responses** through the real SDK (custom `fetch`): request shape, headers, caching, wrapping of untrusted output, append-only history, `max_tokens` and refusal handling. | Proves the integration without a key or network. | Mocking the SDK client (would not test the wire format). |

## Security and access

| # | Decision | Why | Alternatives |
|---|---|---|---|
| S1 | Passwords hashed with **scrypt** (N=2^17, r=8, p=1 on the server via Node's native implementation; N=2^12 in the in-browser demo, where a pure-JS scrypt runs on page load). Hashes self-describe their parameters and are upgraded on sign-in. | Memory-hard, standard, no native dependency in the browser. | argon2id (native module or WASM in the browser). |
| S2 | **Server-side sessions**: opaque random token in an httpOnly, SameSite=Lax cookie (Secure over https), stored only as a SHA-256 hash; 30 min idle, 12 h absolute, rotation every 15 min with a 60 s grace for in-flight requests; revoked on password change, role change, disable and reset. | Revocable, no token in JS. | JWTs (hard to revoke). |
| S3 | **CSRF**: every mutation needs the session's CSRF token in `x-csrf-token`; public mutations (login) need `x-requested-with: bookhand`; cross-origin mutations are refused by an Origin check. | Defence in depth beyond SameSite. | |
| S4 | **Rate limits**: per-IP token buckets for all requests, mutations and agent runs; sign-ins are limited per IP for load, and only **failed** sign-ins, codes and password changes are charged against the strict brute-force bucket (8, refilling one per two minutes); accounts lock for 15 minutes after five consecutive failures. | Found by the e2e test: charging successful sign-ins locked out an office of people switching accounts. | Charging every attempt. |
| S5 | **RBAC** with seven roles (Staff Accountant, AP Clerk, FP&A Analyst, Senior Accountant, Controller, CFO, Auditor read-only, Admin) and per-role approval limits; **SoD rules** in a table (maker-checker, requester self-review limit, policy author cannot check outcomes, vendor master vs payment, admin role conflicts), each blocking or warning (warnings are recorded on the approval and in the audit chain). Maker-checker on manual journals, reconciliation sign-offs, flux approval and task review is also built into those workflows and cannot be switched off. | The brief's roles plus SoD; admins administer but hold no financial approval. | |
| S6 | **TOTP MFA** (RFC 6238, 30 s, ±1 step) with replay protection (used steps recorded), secrets sealed at rest with AES-256-GCM under an HKDF-derived key, QR rendered client-side from a matrix (no third-party image service). | Standard second factor; secrets never stored in clear. | SMS. |
| S7 | **SSO seam**: `IdentityVerifier` contract for OIDC/SAML adapters plus tested account-linking rules (link only by provider subject or once by email to an invited SSO user; never link password accounts by email; no silent provisioning). The protocol verifier itself is not bundled. | The verifier must be a maintained library configured per deployment; the linking rules are where products get breached. | Shipping a half-configured OIDC client. |
| S8 | Strict **CSP** in server mode (`script-src 'self'`, no inline scripts), security headers, JSON body limit, parameterized queries only, output encoding by React (no `dangerouslySetInnerHTML`, enforced by lint). | | |
| S9 | Demo password: the documented dev-only default `bookhand-demo` (override with `BOOKHAND_DEMO_PASSWORD`); the deployment secret is generated into `.data/secret.key` (gitignored) when not provided. Nothing secret is committed. | The brief allows an obvious documented dev default. | |
| S10 | The sign-in page lists the demo users and shows the password only when it is the documented default; a password set with `BOOKHAND_DEMO_PASSWORD` is never published or logged (picking a person then only fills in the email). Static files are served only from inside the web root (separator-checked, malformed URLs refused). | Setting your own password on a shared machine must actually keep it private. | |
| S11 | **Tenant isolation** is enforced in every use case (objects of another tenant answer 404, lists are tenant-filtered) and tested through the API with a second organization; because sign-in identifies a person by email alone, an email address belongs to one account across all organizations. | A second customer must not be able to read or act on the first by guessing ids. | Tenant selector on the sign-in page (more friction for the common case). |
| S12 | **Personal access tokens** (`bh_pat_...`, 256 random bits) are stored as SHA-256 hashes, shown once, always expire (7 to 365 days), carry a scope ceiling (read, or read and decide; read-only roles get read-only tokens), act with the owner's live roles, stop when the owner is disabled, are refused on sign-in, account and admin endpoints, skip CSRF (no cookies are involved), are rate-limited per token and per IP for failures, and label everything they change "Name (via MCP)" or "(via API token)" in the audit log. | Assistants must act as a specific person, never as a service account, and a leaked token must be bounded in time and power. | OAuth for MCP (heavier; no identity provider in the demo). |

## Web and UX

| # | Decision | Why | Alternatives |
|---|---|---|---|
| U1 | **"What's next"** is the home page: a ranked list of what needs this person now (run agents, approvals, recs to certify, flux, sign-offs, package, lock). | The research takeaway: the human queue is the product. | Dashboard of charts. |
| U2 | The **inbox** shows every proposal with why, confidence, evidence, verification checks, risk flags and who may approve it; bulk approve/reject; keyboard (j/k/x/a/r); reject requires a reason. | Review is the bottleneck when agents do the work. | |

The checks found real issues (muted text contrast, a settings link and task cards whose accessible names did not contain their visible text, an unlabeled file input), all fixed. | Works on any static host and in the zero-install demo; accessibility verified, not assumed. | |
| U5 | The **zero-install demo** is one self-contained `index.html` (JS, CSS and fonts inlined), runs the real kernel and agents against the in-memory engine, uses relative paths, hash routing, no service worker, no network, and guards all storage access. | Safe in a sandboxed iframe with an opaque origin. | Mock data UI (would not be the product). |
| U6 | The **landing page** is static HTML and CSS built as a second Vite entry with the app's design tokens (light and dark, WCAG 2.2 AA checked in e2e); pricing tiers are labeled illustrative. ## Testing

| # | Decision | Why |
|---|---|---|
| T1 | Gates: typecheck, lint, unit, integration (MemoryDb, PGlite and a real PostgreSQL server via `scripts/with-postgres.mjs`), skill evals, Playwright e2e of the full demo against the built server, and Playwright checks of the static demo. | The brief's gates. |
| T2 | **Skill evals** are per-skill `evals.json` files run on forks of one seeded fixture (`MemoryDb.fork()`), asserting what each agent must find, how the policy disposes it, and what it must not invent. The first run caught a real bug (a GBP depreciation titled in dollars). | Evals that check outcomes, not prose. |
| T3 | Tests hit nested-transaction deadlocks twice (a read inside a read waits on the same connection forever); the API now has a test that calls every read endpoint as every role with a timeout. | Turn hangs into failures. |
| T4 | Screenshots are produced by a Playwright spec that runs the real demo script on a freshly seeded server (desktop 1440x900, phone 390x844 at device pixel ratio 1), so they show actual states (a flux analysis awaiting approval, a Final package, a locked close) rather than staged ones. The e2e and screenshot specs share one "close round" helper. | Screenshots that cannot drift from the product; reviewing them found C1 and C2. |
